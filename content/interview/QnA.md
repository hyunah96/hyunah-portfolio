## A) `C#`
1. ⭐️ **`Value Type`, `Reference Type` 차이**
   - 값 형식`(Value Type)`은 변수가 실제 데이터 값을 저장하는 형식입니다. 그래서 다른 변수에 대입하면 값이 복사됩니다. **복사된 값은 서로 독립적**이라 한쪽을 바꿔도 다른쪽은 바뀌지 않습니다. 자료형은 `int`,`double`,`struct`,`enum`이 있습니다.
   - 참조 형식`(Reference Type)`은 변수가 **데이터가 있는 곳을 가리키는 참조값**을 저장하는 형식입니다. 다른 변수에 대입하면 참조값이 복사되고 두 변수는 같은 객체를 기리킵니다.
     다른 곳에서 변수값을 변경하면 원본의 변수값도 변경됩니다.
     자료형은 `class`,`string`,`array`,`List`,`Dictionary`가 있습니다.

2. ⭐️ **`Call by value`, `Call by reference`(=`ref / out / in`) 차이**
   - `Call by value`는 값을 복사해서 전달하는 기본 방식이고 `Call By Reference`는 변수의 주소를 참조로 전달하는 방식입니다. `ref / out / in`를 사용하면 변수 자체를 참조로 전달합니다.
   - `ref` : **변수 자체를 참조**합니다. **호출하는 쪽도 받는 쪽도 `ref`여야 합니다.**
   - `out` : **변수를 참조로 전달**해서 **결과를 `out`으로 받습니다.** 
   - `in` : **변수 자체를 참조하지만 읽기 전용이라 수정할 수 없습니다.**

3. **메서드 파라미터로 큰 구조체를 넘길 때 성능을 높이려면 어떤 키워드를 쓸 수 있을까요?**
   - `in`을 사용하면 값을 복사하지 않아도 변수 자체를 참조할 수 있기 때문에 `in`을 사용하는 것이 더 낫다고 생각합니다.

4. ⭐️ **`struct`와 `class`는 어떤 차이가 있고, 각각 메모리의 어느 영역에 할당되는가?**
   - `struct`: **값 형식**이라 값이 복사돼서 서로 독립적입니다. `null`이 안 되고 상속도 안 됩니다. 기본적으로 `Stack` 영역에 할당됩니다.
   - `class`: **참조 형식**이라 참조값이 복사되어 같은 객체를 공유하고 `null`이 가능하며 상속이 가능합니다.  기본적으로 `Heap` 영역에 할당됩니다.

5. **`Stack`, `Heap` 개념**
   - `Stack`: 메서드 호출 동안만 쓰는 **지역변수, 매개변수, 참조형 변수의 참조값**이 쌓이는 곳으로 메서드가 반환되면 즉시 정리가 됩니다.
   - `Heap`: **객체의 실제 데이터**가 저장되는 곳으로 참조가 끊어지면 GC가 관리합니다.
 
6. ⭐️ `int.Parse` 대신 `int.TryParse`를 쓰는 이유가 무엇인가요?
   `TryParse`, `TryGetValue` Try 패턴 의미
   - `TryParse`, `TryGetValue`는 실패가 날 수도 있는 상황일 때 `true`,`false`로 반환해서 **예외를 방지합니다. 성공했을 때의 결과 값을 `out` 매개변수로 전달합니다.**
  
7. ⭐️ **`string` immutable(불변) 개념**
   - `string`은 **불변** 이라서 한 번 만들어지면 **수정할 수 없습니다.** 문자열을 수정하게 되면 기존 문자열을 바꾸는 게 아니라 **새 문자열 객체가 생성**됩니다. 그래서 여러번 이어 붙이는 작업은`StringBuilder`를 사용하는 것이 좋습니다.


8. ⭐️ **`static` 키워드의 의미와, `static` 멤버를 남용했을 때 발생할 수 있는 문제점이 무엇일까요?**
   - `static`은 객체를 만들지 않아도 클래스 이름으로 바로 접근할 수 있습니다. 프로그램 전체에서 1개의 값만 갖고 있습니다.
   - `static` 멤버는 모든 인스턴스가 같은 값을 보기때문에 공유 상태가 생겨서 유지보수에 어려움이 생길 수 있습니다.


9. **`Boxing`과 , `Unboxing`이 무엇인지 설명해주시고, 이게 성능에 왜 안 좋은 영향을 주는지 연결해서 답해주세요.**
   - `Boxing`은 값 형식을 `object`로 변환하면서 `Heap`에 새 객체를 만들고 값이 복사되는 과정을 말합니다. `stack`에 있는 참조값을 복사해 새로운 객체에게 넣기때문에 많은 `Boxing`은 메모리 부담이 발생할 수 있습니다.
   - `Unboxing`은 박싱된 `object` 안의 값을 **원래 값형식으로 꺼내는 과정**을 말합니다. 
     원래 값 형식 타입으로의 캐스팅이 필요하고 타입이 맞지 않으면 예외가 발생합니다.
   
10. ⭐️ **`var`, `dynamic` 차이**
   - **`var`** 는 **컴파일타임에 오른쪽 값을 보고 타입을 결정**합니다. 한 번 정해진 타입은 바뀌지 않습니다. (**정적 타입**)
   - **`dynamic`** 은 **런타임에 실제 들어있는 값의 타입을 보고 결정**합니다. **동적 타입**이고 대입할 때마다 타입이 달라질 수 있습니다.

11. **`object`란?
   - `object`는 **최상위 타입**이라 무엇이든 담을 수 있지만, 사용할 땐 **캐스팅이 필요**하고 값형식을 담을 땐 **박싱/언박싱**이 발생할 수 있습니다. (**참조형식**은 **박싱/언박싱이 필요 없**)


12. ⭐️ `nullable`(`int?`), `null` 처리 연산자(`??`, `??=`)
   - `nullable`: `null` 허용하는 타입
```csharp
int? age = null;             // null 허용
int safeAge = age ?? 0;      // null이면 0

name ??= "Unknown";          // name이 null일 때 대입
```

13. `==`, `Equals` 차이
   - `string`은 `==`도, `Equals`도 **둘 다 값 비교**로 동작합니다.
     `"a" == "a"` true, `"a".Equals("a")` true
   - **참조형**에서는 `==`,`Equals` 둘 다 **참조 비교**로 동작합니다.

14. **`const`, `readonly` 차이** (캡슐화할 때 사용하는 키워드)
    - **`const`** 는 **컴파일 타임 상수**로 컴파일 타임에 값이 확정됩니다. **선언할 때 초기화**를 해야하고 **컴파일 타임에 계산 가능한 값**만 가능합니다.
    - **`readonly`** 는 **런타임 상수**로 **선언할 때 초기화 하거나 생성자에서 딱 한 번 값 할당**이 가능합니다. **참조를 다른 객체로 변경하는 건 안되지만 객체 내부 값 변경은 가능**합니다.

15. **필드를 `private`으로 두고 프로퍼티로 접근하게 만드는 이유가 무엇인가?**
   - 필드를 `public`으로 열어두면 외부에서 마음대로 값을 변경할 수 있습니다. 프로퍼티를 사용하면 `set` 으로 값 유효성 검사를 할 수도 있고, `private`으로 선언해서 내부 데이터를 숨길 수 있어 안전하게 관리할 수 있습니다.

16. **다형성 개념**
    - 다형성은 **메서드를 호출했을 때 타입에 따라 다르게 동작하는 것을** 말합니다.
      **컴파일 타임 다형성으로는 오버로딩**이 있고 **런타임 다형성으로는 오버라이딩,인터페이스** 가 있습니다.

17. ⭐️ **`Overloading`, `Overriding` 차이**
    - 오버로딩은 **매개변수(개수/타입/순서)를 다르게 해서** 컴파일 타임에 어떤 메서드를 호출할지 결정하는 방식입니다.
    - 오버라이딩은 **부모의 메서드를 자식이 재정의하는 방식입니다.** 자식은 부모 메서드와 시그니처가 같아야 합니다.
      
18. **`virtual / override / new` 차이 (알아만 놓기)**
    - 오버라이딩에 사용하는 키워드로 **부모 메서드**에는 `virtual`을 **자식 메서드**에는 `override`를 붙인다.
    - `new`는 **부모 메서드를 숨기고** 변수 타입에 따라 호출이 달라지는 건데 **다형성은 아님**

19. **인터페이스, 추상 클래스 차이**
	- 인터페이스는 **클래스가 기능을 반드시 구현해야 하는 규칙**입니다. 클래스는 여러개의 인터페이스를 다중 구현할 수 있습니다.
	- 추상 클래스는 **공통 필드나 공통 로직같은 기본 구현을 제공합니다.** 추상 메서드로 남기면 자식은 반드시 구현해야 하고 **단일 상속이라 하나만 상속 가능**합니다. 
	

20. **객체지향 프로그래밍에 대해 설명해보세요.**
   - 객체 지향 프로그래밍(OOP)은 프로그램을 데이터와 기능을 객체 단위로 나눠서 설계하는 방식입니다. 객체 지향의 4대 특성으로는 **캡슐화, 상속, 다형성, 추상화**가 있습니다.

19. OOP 4대 특성(캡슐화/상속/다형성/추상화)
    - **객체지향 4대 특성은 캡슐화, 상속, 다형성, 추상화입니다.**  
      1. ⭐️**캡슐화**는 객체의 내부 데이터를 `private`으로 숨기고, 메서드/프로퍼티로만 접근하게 해서 **무결성을 지키는 것**입니다.  
      2. **상속**은 공통 기능은 부모 클래스에 두고, 자식 클래스가 이를 재사용하면서 필요한 기능을 **추가해서 확장**하는 방식입니다.  
      3. **다형성**은 부모 타입으로 다루더라도 실제 객체 타입에 따라 `override`된 메서드가 다르게 동작하는 것입니다. 
      4. **추상화**는 인터페이스/추상 클래스로 **무엇을 할 수 있는지**만 정의하고 상세 구현은 감춰서, 구현체를 바꿔도 사용하는 코드는 그대로인 **교체 가능한 구조**를 만듭니다.

20. 객체란?
   - 클래스에 정의된 데이터나 메서드를 실제로 가진 단위

19. 캡슐화에서 `private`로 숨기는 이유
      -  **외부에서 직접 수정하지 못하게 막고**, 필요한 기능만 공개해서 **정해진 방식을 통해서만 접근하게 하기 위함입니다.**

20. **좋은 코드란 무엇인가요?**
   - 제가 생각하는 좋은 코드는 클래스 별로 필요한 기능만 분리해서 구현하는 것입니다. 그렇게하면 나중에 어떤 기능이 수정되더라도 그 기능을 쓰지 않는 다른 클래스들은 영향을 주지않아 유지보수가 수월해지기 때문입니다.

19. SOLID 5대 원칙
	- **SOLID는 객체지향 설계를 할 때 유지보수가 쉽고 확장하기 좋게 만드는 5가지 원칙입니다.**
    - **SRP** - **하나의 클래스는하나의 책임**만 가져야 합니다.
    - **OCP** - **새로운 기능이 추가되어도 기존 코드 수정은 최소화** 하는 원칙입니다.
    - **LSP** - 서브 타입은 언제나 부모 타입으로 교체할 수 있어야 한다는 원칙입니다. (다향성)
    - **ISP** - **인터페이스를 각각 사용에 맞게끔 잘게 분리해야 한다는 원칙**입니다.
    - **DIP** - 어떤 **`Class`를 참조해서 사용할 때 그 `Class`를 직접 참조하는 것이 아니라 상위 요소로 참조**하라는 원칙입니다.

20. **본인이 생각했을 때 가장 중요하게 생각하는 원칙 하나는?**
   - ISP입니다. 각 클래스 별로 필요한 기능만 분리해서 구현하면 나중에 특정 기능이 수정되더라도 그 기능을 쓰지 않는 다른 클래스들에는 영향을 주지 않아 유지보수가 훨씬 수월해집니다.

19. **상속, 합성**
    - **상속**은 공통 기능은 부모 클래스에 두고, 자식 클래스가 이를 재사용하면서 필요한 기능을 **추가해서 확장**하는 방식입니다.  
      단점으로는 **결합도가 높아지고**, 부모의 변경이 자식에게 영향을 줄 수 있습니다.
    - **합성**은 다른 객체를 멤버로 포함해 **위임**하는 방식이라, 기능을 쉽게 확장할 수 있고 **유지보수성이 좋습니다.**

20. **결합도가 무엇인가?**
    - **결합도는 서로에게 얼마나 의존하고 엮여있는지에 대한 정도입니다.**  결합도가 높으면 한쪽 변경이 다른 쪽에 영향을 줘서 유지보수가 어려워집니다. 그래서 **결합도는 낮게** 설계하는것이 좋습니다.

21. **`DateTime`/`TimeSpan` 차이**
    - `DateTime` : **타임스탬프**, 현재 로컬 PC의 시간을 나타냅니다.
      `DateTime`끼리 빼면 `TimeSpan`이 나온다는 것은 참고 
    - `TimeSpan` : **두 시점 사이의 차이**를 나타냅니다.
      `end - start`로 `TimeSpan`을 구해서 소요시간이나 타임아웃 계산에 쓴다 참고

22. **언제 if로 미리 막고, 언제는 try/catch로 처리하는가?**
	- 입력값처럼 **예상 가능한 오류**는 `if`, `TryParse`로 검증합니다.
    - DB나 네트워크 같은 **외부 자원은 언제 예외가 발생할지 예측이 어렵기 때문에** `try/catch`로 예외 처리합니다.

23. try-catch-finally
    - **try**: 예외가 날 수 있는 코드를 시도하는 블록
	- **catch**: 예외가 발생했을 때 처리하는 블록
	- **finally**: 예외가 나든 나지않든 **실행**되는 블록


24. GC가 해주는 것, 못해주는 것
    - **GC가 해주는 것** : 더이상 **참조되지 않는 메모리를** 회수합니다.(`new`로 만든 객체의 메모리)
    - **GC가 못해주는 것**: 통신이나 DB 연결 같은 자원은 원하는 시점에 확실히 닫아주지 못합니다. (왜? GC는 언제 작동하는지에 대한 시점을 보장받을 수 없기때문에)

25. `using` / `IDisposable` 개념(자원 해제)
    - `IDisposable` : 통신이나 DB 연결을 `Dispose()`로 자원을 해제해줍니다.
    - `using` : `IDisposable` 객체를 사용 후 **스코프가 끝날 때 자동으로 `Dispose()`를 호출합니다. 예외가 발생해도 자원 해제가 보장됩니다.**

26. `delegate`, `event` 차이 
    - `delegate`는 **메서드 참조를 담는 타입**입니다. 시그니처가 **완전히 같은 메서드만** 연결할 수 있습니다.  외부에서 직접 호출(`Invoke`)도 가능합니다.
    - `event`는 `delegate` 기반의 알림용 멤버입니다. 외부에서는 `+=`/`-=` 구독, 해제만 가능하고 직접 호출(`Invoke`)은 이벤트를 선언한 클래스 안에서만 가능합니다.

27. `LINQ`는 무엇인가?, 장단점
    - `LINQ`는 데이터를 **쿼리 형식으로 조회**할 수 있게 해주는 기능입니다.
      **장점**으로는 **가독성**이 좋고 **타입 안정성**이 보장됩니다.
      **단점**으로는 **여러번 열거하면** 계산이 중복될 수 있고 **지연 실행**으로 인해 언제 쿼리가 실행되는지, 어디서 오류가 발생하는지 파악하기 어려울 수 있어서 디버깅이 어렵습니다.

28. LINQ의 **지연 실행**이 무엇인가요?
    - 쿼리가 선언된 시점이 아니라 **데이터가 열거될 때 실행되는 것**을 말합니다.

29. 그럼 **즉시 실행**을 하려면 무엇을 사용하나요?
    - `ToList()`,`ToArray()`를 사용하면 **호출할 때마다 바로 실행되고 결과가 고정**됩니다.

30. **LINQ `Where` 결과는 언제 실행되나요?**
    - **열거**가 일어나는 순간에 실행됩니다.

31.  **쿼리를 두 번 열거하면 어떤 일이 생겨요?**
  지연 실행 쿼리는 열거할 때마다 계산이 반복될 수 있고 원본이 바뀌면 결과가 달라질 수 있습니다.

%% 15. `IEnumerable`, `IEnumerable<T>` 차이
    - `IEnumerable`는 **비제네릭**이라 열거할 때 **요소가 `object`로 나오고, 필요하면 캐스팅이 들어가서 타입 안정성이 떨어집니다.**
	- `IEnumerable<T>`는 **제네릭**이라 **요소가 `T` 타입으로 나오기 때문에 캐스팅이 필요 없고 타입이 안정적입니다.** %%


16. `List<T>`, `Dictionary<TKey,TValue>` (둘 다 동적이다.)
    - `List<T>` : **같은 타입의 요소를 순서대로 저장하는 컬렉션입니다.**
      **인덱스로 접근** 가능하고 **순서와 중복을 허용**합니다.
    - `Dictionary<TKey,TValue>` : **키와 값을 한 쌍으로 저장하는 컬렉션으로 키는 유일해야 합니다.(중복X)** **키로 접근해서 빠르게 조회하는 용도**로 사용됩니다.
      - **선택 기준** : 순서가 중요하거나 전체를 순회하면서 처리하려면 `List`,
        빠르게 찾는 것이 핵심이면 `Dictionary`

  - 수만 개의 데이터 중 특정 키값으로 데이터를 빠르게 찾아야 한다면 어떤 컬렉션을 쓰시겠어요? 그 이유는요?
    - `Dictionary<TKey, TValue>`를 사용하겠습니다. `List<T>`는 처음부터 끝까지 순회해야 해서 데이터가 많아질수록 속도가 느려지지만, `Dictionary`는 **해시 테이블** 구조를 사용하기 때문에 데이터 양과 상관없이 빠르게 값을 찾을 수 있기 때문입니다.

  - **`Dictionary`에서 키가 중복되면 어떻게 되나요?**
    - `Add`는 키가 없으면 추가되고 키가 중복되면 예외가 발생합니다.
    - `indexer`는 (`dict[key] = value`)는 키가 없으면 추가되고 키가 중복되면 덮어쓰기됩니다.

14. `Dictionary` 키 비교 `Equals`, `GetHashCode` 차이
    - `Dictionary`는 키를 찾을 때 `GetHashCode`로 위치를 찾고 후보가 여러 개면 `Equals`를 사용해서 같은 키인지 확인합니다.

15. **접근 제한자(`public`/`private`/`protected`/`internal`)**
    - `public` : 어디서든 접근 가능합니다.
    - `private` : **같은 클래스 내부에서만 접근 가능**합니다.
    - `protected` : **같은 클래스이면서 자식 클래스만 접근 가능**합니다.
    - `internal` : **같은 프로젝트 안에서만 접근 가능**합니다.

## B) `WPF`
1. **WPF와 WinForms 차이**
   - **WPF** : **XAML을 사용하여 UI를 구성**합니다. **데이터 바인딩**으로 **UI와 로직을 분리**해서 유지보수성이 좋습니다.
   - **WinForms** : 컨트롤을 코드로 배치하고 이벤트 중심으로 처리하는 방식이라 기능이 커질수록 복잡해지고 유지보수가 어려워질 수 있습니다.

2. **XAML, Code-behind의 역할**
   - **XAML** : 레이아웃, 스타일, 데이터 바인딩을 선언해서 화면(View)을 구성합니다.
   - **Code-behind** : UI에 관련된 것만 처리하고 데이터 처리같은 비즈니스 로직은 ViewModel이 수행합니다.
 
3. **Data Binding, DataContext** 
   - **Data Binding** : **XAML의 UI 속성과 ViewModel의 속성을 연결해서** 데이터의를 전달해주는 역할을 합니다. 
   - 장점 : 값이 바뀔 때마다 **UI를 직접 업데이트하는 코드를 줄일 수 있어서** 유지보수가 쉬워집니다.
   - **DataContext** : 바인딩이 값을 찾을 때 기준이 되는 **기본 데이터 소스** 입니다.

2. 모델(ViewModel)의 값이 바뀌었을 때 화면에 즉시 반영되게 하려면 어떤 처리가 필요한가요? or 데이터가 바뀐 걸 `View`가 어떻게 알죠?
   - `ViewModel`에서 `INotifyPropertyChanged` 를 등록하면 값이 변경될 때마다 `PropertyChanged`로 이벤트를 발생시킵니다.

2. **`View`와 `ViewModel`은 어떻게 연결하는가?**
   - `View`의 `DataContext` 속성에 `ViewModel`의 인스턴스를 **연결**합니다.

3. `Binding Mode` 설명
   - `Binding Mode`는 **데이터가 어느 방향으로 흐를지**를 정하는 옵션입니다.
   - `OneWay`: 한방향으로 `ViewModel` 값이 바뀌면 `UI`는 갱신되지만, `UI`에서 값을 바꿔도 `ViewModel`에는 반영되지 않습니다. VM → UI
   - `TwoWay`: 양방향으로 `ViewModel`에서도, `UI`에서도 값이 바뀌면 서로 갱신됩니다. VM ↔ UI
   - `OneTime`: 처음 한번만  `ViewModel`값을 `UI`로 가져옵니다.

4. `TextBox`는 어떤 것을 사용하나요?
 - `TextBox`는 사용자 입력을 `ViewModel`에 반영해야 해서 보통 `TwoWay`로 씁니다.

2.  입력 값은 언제 `ViewModel`로 들어가나요?
   - 포커스가 빠질 때 반영됩니다. 타이핑 즉시 반영이 필요하면 `UpdateSourceTrigger`를 사용합니다.


2. **레이아웃과 패널**
    - 레이아웃 종류로는 `Grid`, `Canvas`, `StackPanel`, `DockPanel`, `WrapPanel`이 있습니다.
    - `Grid` : 화면을 행과 열로 나눠서 배치하는 레이아웃입니다.
    - `Canvas` : 내가 지정한 좌표(X,Y) 위치에 그대로 배치하는 레이아웃입니다. 
    - `StackPanel` : 컨트롤을 한 방향으로 쌓아서 배치합니다. **기본값은 수직**으로 배치합니다.
      수평으로하면 왼쪽에서 오른쪽 순서대로 배치합니다.
    - `DockPanel` : 컨트롤을 **상,하,좌,우** 중 하나에 붙여놓습니다. **마지막 컨트롤은 남는 공간을 전부 차지합니다.**
    - `WrapPanel` : 컨트롤을 **왼쪽에서 오른쪽으로 배치하다가 공간이 부족하면 자동으로 다음줄로 내려가서 배치합니다.**
  
3. `Resource`(`Brush`,`Thickness`, `Style`), `ResourceDictionary` 설명
    - `Resource`: XAML에서 `x:Key`로 저장해두고 재사용하는 것을 말합니다. 
      리소스 `Key`로 등록해서 스타일을 여러 컨트롤에서 공통으로 사용할 수 있습니다.
      **리소스가 많아지면 `ResourceDictionary` 파일로 분리해서 관리합니다.**

4. 정적 리소스(`StaticResource`), 동적 리소스(`DynamicResource`)의 차이
   - **`StaticResource`: XAML이 로드될 때 리소스를 찾아서 값이 고정**됩니다. 
   - **`DynamicResource`:** 실행 중에 리소스가 바뀌면 **다시 참조해서 UI에 반영**할 수 있습니다.

2. `StaticResource`로 스타일을 찾을 때 어디서부터 찾는가?
   - 현재 요소의 `Resources` → 부모 → `Window.Resources` → `App.Resources`
    

2. WPF에서 **목록 UI에 데이터 붙일 때 뭘 쓰나요?**
   - 목록 `ItemsControl`: `ListBox(목록)`, `ListView(표)`, `DataGrid(표)`, `ComboBox(드롭다운)`

2. **`List<T>`, `ObservableCollection<T>`차이**
   - `List<T>`: **데이터는 바뀌지만 변경 알림이 없어서 UI가 자동 갱신되지 않을 수 있습니다.**
   - `ObservableCollection<T>`: **데이터가 변경되면 UI가 자동으로 갱신됩니다.**


1. **Command(ICommand)**
   - `Command`는 `View`의 사용자 입력을 `ViewModel`로 연결해주는 통로입니다. `View`는 `Command`를 바인딩해서 실행 요청만 하고 실제 처리 로직은 `ViewModel`에 두어서 UI와 비즈니스 로직을 분리합니다.

- **ICommand를 쓰는 이유가 무엇인가요?**
 - `ICommand`를 쓰면 이벤트 핸들러 대신 `Execute`,`CanExecute` 로 동작을 캡슐화할 수 있어서 **재사용**하기에 좋습니다.

- **Command, code-behind 차이**
  - **code-behind**는 View 코드에 로직이 들어가서 UI와 쉽게 결합되고, 화면이 커질수록 유지보수가 어려워집니다.
	**Command** 는 `View`가 실행 요청만 하고 로직은 `ViewModel`에 있어서 **재사용**에 좋습니다.


1. “부모 `Grid`에 `FontSize=16` 을 줬더니 안쪽 `TextBlock`도 커지던데 왜인가?
   - WPF의 일부 속성은 **값 상속** 이 적용돼서 부모에 설정한 값이 자식 요소로 전파됩니다.  **만약 자식이 `FontSize`를 따로 지정하면 그 값이 우선** 적용됩니다.

1. **UI Thread & Dispatcher 개념**
   - 화면을 그리거나 컨트롤을 업데이트하는 작업은 **UI Thread**가 담당합니다. 다른 스레드에서는 UI 컨트롤을 직접 변경할 수 없고 **Dispatcher**를 통해서 **UI Thread**로 작업을 전달해야 합니다.
   - **Dispatcher**는 **UI Thread**가 처리할 작업을 모아두는 작업 큐 입니다. 새 스레드를 만드는 것이 아니고 **UI Thread**의 큐에 작업이 추가돼서 순차적으로 처리됩니다.
   
2. **백그라운드 스레드에서 UI 요소의 값을 수정하면 어떻게되나요? 해결 방법은?**
 - UI 컨트롤을 생성한 UI 스레드만 해당 객체에 접근할 수 있도록 제한했기 때문에 다른 스레드에서 접근하면 에러가 발생합니다.

- **Dispatcher는 언제 써야 하나?**
  - UI 요소는 UI 스레드에서만 접근 가능해서, **백그라운드 스레드에서 UI를 바꿔야 할 때 Dispatcher로 UI 스레드에 작업을 보내야 합니다**

## C) 디자인 패턴(MVC,MVVM)
76. **디자인 패턴이란?**
    - 클래스랑 객체를 어떻게 나누고 연결할지에 대한 설계 규칙

77. **Scenario 모델링이란 무엇인가?
    - 사용자 관점에서 시스템이 어떻게 동작해야 하는지 시나리오로 기술하는 것을 말합니다. 프로그램을 사용하는 과정을 미리 시뮬레이션함으로써 **요구사항 누락을 방지**하고, **설계 방향을 일치**시키는 과정입니다.

78. **MVVM 패턴 설명**
    - `Model`, `View`, `ViewModel`의 약자로 화면과 로직, 데이터를 분리하는 패턴입니다.

79. **WPF에서 왜 MVVM패턴을 쓰는가?**
    - WPF에는`Data Binding`과 `Command`를 통해 UI와 로직을 분리할 수 있어서 의존성을 낮추고 유지보수성과 재사용성을 높이기 위해 MVVM패턴을 사용합니다.

80. **MVC패턴 설명**
    - `Model`, `View`, `Controller`의 약자로 화면과 로직, 데이터를 분리하는 패턴입니다.

81. **MVC 패턴과 MVVM 패턴의 차이점**
    - MVC 패턴은 `Controller`가 요청을 받아 `Model`을 갱신한 뒤 결과를 `View`에 반영합니다.
    - MVVM 패턴은 `Data Binding`과`Command`로 `View`와 `ViewModel` 을 연결하고, `ViewModel`이 화면 상태와 동작을 담당합니다.

82. WPF 프로젝트에서 왜 굳이 MVVM 패턴을 도입해야 하나요? MVC와 비교했을 때 어떤 장점이 있죠?
    - MVC는 Controller가 View를 직접 알고 제어하는 경우가 많아 결합도가 높습니다.
      MVVM은 **데이터 바인딩** 덕분에 ViewModel이 View 참조가 없어도 동작합니다.

83. 디자인 패턴 중에서 MVVM 말고 들어보거나 공부하신 다른 패턴이 있는가?
    - 싱글톤 패턴,옵저버 패턴을 알고있습니다.

## D) 비동기(Async/Await)

1. **비동기란?**
   - 다른 작업을 기다리는 동안 스레드를 막지않고 작업이 완료되면 이어서 실행하게 만드는 방식입니다.
   - `async`는 **비동기 메서드를 선언할 때 사용하는 키워드**입니다.
   - `await`은 **비동기 작업이 완료될 때까지 메서드의 실행을 일시 중단하고 작업이 완료되면 메서드의 실행을 계속 진행하게 합니다.**

1. WPF에서 async/await를 쓰는 근본적인 이유가 무엇인가요?
   - 다른 작업을 수행하는 동안 **ui스레드가 멈추지않고 화면이 멈추지않고 계속 반응하도록** 하기 위해서 입니다.

2. await 하면 스레드가 하나 더 생기나?
   - **작업 완료를 기다렸다가** 이어서 실행하는 거라서 **스레드를 새로 생성하지 않습니다.**

- **await 뒤에 UI 업데이트가 되는 이유는?**
  - `await`의 작업이 끝난 후에 다시 UI Thread로 돌아와서 작업을 이어주기 때문입니다.

1. 동기, 비동기 차이
  - 동기 : 작업이 완료되어야만 다음 작업이 시작되는 방식
  - 비동기 : 작업이 완료되지 않아도 다음 작업이 시작될 수 있는 방식

1. 왜 비동기를 사용하는지?
   - **동기는 작업 완료를 기다리느라 UI가 멈추지만 비동기는 기다리는 동안 다른 작업을 할 수 있어 UI를 유지할 수 있기 때문입니다**.


1. **`async void`가 왜 위험한가?**
   - `async void`는 **예외 처리가 불가능하기 때문에 어디서 예외가 일어났는지 추적하기 어렵습니다.**
    
1. **`async`, `Thread` 차이**
   - `async`: 다른 작업을 기다리는 동안 스레드를 막지않고 작업이 완료되면 이어서 실행하게 만드는 방식입니다.  (`async`,`await` 는 **스레드 생성이 아님!!**)
   - `Thread` : **코드를 실제로 실행하는 실행 단위**라서 스레드를 만들면 실행 흐름이 더 생겨서 **병렬 실행**이 가능합니다.

## E) 멀티스레드
63. 멀티스레드란?
    - 하나의 프로세스 내에서 두개 이상의 스레드를 동시에 동작하는 것을 말합니다.
64. 스레드가 여러 개일 때 생길 수 있는 문제는?
    - 스레드가 많아지면 **경쟁 상태**가 발생합니다. 경쟁 상태는 **동시에 접근해서 값을 수정하려고 할 때 실행 순서에 따라 결과가 매번 달라지는 문제를 말합니다.**

65. 경쟁 상태가 왜 발생하는가?
    - CPU가 스레드를 교체하는 타이밍을 예측할 수 없기 때문입니다. 방지방법 : `lock`

66. `lock`이란?
    - **여러 스레드가 동시에 데이터를 건드리지 못하게 막아두는 것**으로 알고있습니다.

## F) DB/SQL 기본

68. 실행 순서 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`

69. **WHERE, HAVING 차이**
    - **WHERE**:  SELECT 조건을 필터링
    - **HAVING**: GROUP BY의 조건을 필터링

70. **JOIN 기본 개념 INNER, LEFT JOIN 차이**
    - **JOIN**: 두 테이블을 공통 키로 결합하여 조회하는 것
    - **INNER JOIN**: 교집합
    - **LEFT JOIN**: 왼쪽 테이블 기준으로 매칭되는 것만 가져오는 것
    
71. **GROUP BY가 필요한 상황, 집계 함수(COUNT/SUM/AVG)**
    - 그룹별로 합계나 평균 등을 구하고싶을 때 사용

72. **PK, FK, 왜 필요한지**
    - **PK**: 테이블에서 각 행을 유일하게 식별하는 키, (중복,NULL X)
    - **FK**: 다른 테이블을 기본키를 참조해서 테이블 간의 관계를 연결하는 키 (데이터 무결성 보장)
        
73. **정규화**
    - 중복을 줄이기위해 데이터를 테이블로 분리하는 것

74. **인덱스란?**
    - 특정 컬럼을 빠르게 찾을 때 사용

75. **트랜잭션**
    - **SQL 작업을 하나의 작업 단위**로 묶어서 전부 성공(COMMIT)하거나 전부 취소(ROLLBACK)하게 하는 것
        
76. **NULL 비교**
    - `= NULL` 불가 `IS NULL` 또는 `IS NOT NULL`을 사용

77. **서브쿼리**
    - 한번 더 데이터를 필터링해야될 때 사용

##### 영업 상담에서 개발자로 바뀐 계기는?

매일 아침 9시에 업무가 시작되면 상담원별로 담당 고객 DB가 자동으로 배정됩니다. 
해당 점포의 위치, 담배 재고, 연락처 같은 정보를 확인한 후에 점주님과 통화하며 상담을 진행했습니다. 그 과정에서 다른 상담원들과 담당 DB가 겹치지 않게 배정되는 것과 통화 후 녹취는 어디에 어떻게 저장이 되는지 주문건은 어떻게 배송기사에게 전달되는지가 궁금했습니다. 이런 호기심이 점점 커지면서 자연스럽게 프로그램에 관심을 갖게 된 것 같습니다.

**그래서 고객 DB는 어떻게 겹치지않게 배정되었을까?**
제 생각에는 고객 테이블에 담당자 필드가 따로 있어서 겹치지 않았을 것 같습니다.

##### WEB-APP-PLC 통신 구조를 설명해보세요.
Web은 관제 UI라 서버 API를 HTTP로 호출했고, 상태는 폴링 방식으로 주기적으로 조회해 화면을 갱신했습니다. PLC는 MQTT 기반으로 서버의 브로커(모스키토)에 연결해 상태를 Publish하고 제어 명령을 구독했습니다. 드론 제어는 DJI SDK 제약 때문에 Web에서 직접 불가능해서, DJI SDK가 있는 App이 실제 제어를 수행했고 Web의 요청은 서버를 거쳐 App으로 전달되는 방식이었습니다


##### MQTT를 쓴 이유는? HTTP랑 뭐가 달라요?
- 클라이언트에서도 서버를 폴링하고 서버에서도 PLC를 폴링하는 과정에서 PLC 연결이 지속적으로 끊기는 문제가 있었습니다. 그래서 서버는 PLC를 구독하고 PLC는 상태 변화가 일어날때마다 서버에게 이벤트를 발행하는 방식을 선택했습니다.

#####  드론 스테이션 관제 시스템 웹개발에서 어려웠던 점은? 
- 네트워크 상태에 따라 화면이 멈추면 드론이 멈춘 것처럼 느껴져서 혹시 모를 대비를 위해 드론을 조종할 수 있는 직원에게 근처에 잠시 있어달라고 부탁했던 적이 많습니다. 화면에 비행 위치가 보이지 않으면 추락을 했는지 안 했는지 알 수가 없기 때문에 불안했던 경험이 많습니다.

##### 협업(중국)팀과 갈등,이슈 있었나요?
- 갈등은 없었지만 소통하는데 시간이 조금 걸렸습니다. 같이 있는 상태가 아니어서 어떤 부분을 개발을 했을 때 또는 변경 되었을 때 각자의 환경에서 잘 되는지 테스트하려면 서로의 일정을 확인하고 날짜를 맞춰야하는 과정에서 시간이 조금 걸렸던 것 같습니다.
