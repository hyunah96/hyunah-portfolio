## 반도체 장비는 어떻게 ‘대화’할까?

반도체는 아주 정밀한 공정을 거쳐 만들어지는 제품이다.
그렇다면 반도체 공장에서  수많은 장비들은 어떻게 서로 소통할까? 
사람이 매번 버튼을 누르고 상태를 확인하며 장비를 움직이는 방식이 아니라, 공정 현장에서는 **장비**와 **시스템(MES/EAP)** 이 끊임없이 데이터를 주고받으며 장비를 모니터링하고 제어한다. 
이때 장비와 시스템을 연결해 주는 대표적인 표준이 바로 **SECS/GEM 프로토콜**이다.

---
## SECS/GEM(E5/E30/E37)

현업에서는 보통 SECS/GEM을 아래처럼 **층(layer)** 으로 이해한다.
- **SECS-II (E5)**: 무슨 내용을 주고받는지 → **메시지 포맷/데이터 타입/구조**
- **HSMS (E37)**: 어떻게 보내는지 → **TCP 기반 전송/세션/타임아웃/재연결**
- **GEM (E30)**: 장비가 무엇을 제공해야 하는지 → **장비 동작 모델(상태/이벤트/알람/커맨드)**

- E37(HSMS)이 "길(전송)"을 만들고
- E5(SECS-II)가 "대화 내용(메시지)"을 정의하고
- E30(GEM)이 "장비가 어떤 규칙으로 말해야 하는지(기능 모델)"를 정한다.
---
## SECS

반도체 **장비와 시스템이 서로 통신**할 수 있도록 하는 **일련의 통신 프로토콜 및 메시지 형식**이다.
- 장비 ↔ 시스템 사이에 표준화된 메시지 형태로 데이터를 주고받기 위한 규칙
---
## GEM

장비가 **어떤 기능/상태/이벤트를 어떤 규칙으로 제공해야 하는지** 정해둔 **장비 동작 모델 표준**이다.
- 어떤 상태를 가져야 하고, 어떤 이벤트/알람을 보고해야 하고, 원격 명령을 어떤 형태로 받아야 하는지 "장비의 행동 규약"이 GEM이다.

### 1) HSMS (E37)

HSMS는 TCP 기반으로 동작하며, 다음 포인트들이 중요하다.

## 연결/세션

- 장비와 호스트는 **지속 연결**을 유지한다.
    
- 연결이 끊기면 재연결 로직이 필요하다.
    

## 타임아웃(Timeout)과 재시도

- 요청을 보냈는데 응답이 일정 시간 안에 안 오면 타임아웃 처리
    
- 타임아웃이 반복되면 세션 종료/재연결/장비 상태를 Offline 처리하는 정책이 필요
    

> 포인트: 현업에서 “가끔씩 끊긴다”는 거의 항상 **타임아웃/재연결/멀티스레드 처리**와 연결됨.

## 다중 장비 연결

- 장비가 1대가 아니라 N대가 되면  
    **동시 연결 + 동시 이벤트 수신 + 동시 처리**가 필요하다.
    
- 그래서 C#에서 비동기/멀티스레드를 요구하는 경우가 많다.

# 2) SECS-II (E5): 메시지 구조를 이해하면 절반은 끝

SECS-II는 “메시지의 내용”을 정의한다.

## SxFy 구조

SECS 메시지는 흔히 **SxFy** 형태로 부른다.

- S: Stream (대분류)
    
- F: Function (세부 기능)
    

예: `S1F13`, `S6F11` 같은 식

실무적으로는 “이 메시지가 상태 조회인지 / 이벤트인지 / 알람인지 / 명령인지”를 구분하는 감각이 중요하다.

## 데이터 타입 / 리스트 구조

SECS는 데이터를 그냥 문자열로 보내는 게 아니라,  
정해진 타입과 리스트 구조로 보낸다.

- 정수/실수/문자열/바이너리 등 타입이 명확함
    
- 데이터가 여러 개면 **List로 중첩**되기도 함
    

> UI/Scenario 모델링을 한다면, 이 “중첩 구조”를 **트리/테이블 모델**로 잘 풀어내는 능력이 바로 실무 역량이 된다.

# 3) GEM (E30): “장비가 제공해야 하는 핵심 기능” 5종 세트

GEM은 장비가 시스템에게 제공해야 하는 기능을 모델로 정의한다.  
아래는 GEM에서 거의 무조건 등장하는 핵심 요소들이다.

## 3-1. 상태(State Model)

장비는 “현재 어떤 상태인지”를 시스템이 알 수 있게 해야 한다.

대표적으로

- Online / Offline
    
- Remote / Local  
    같은 운영 상태가 있다.
    

> 실무 포인트: UI에서는 상태를 단순 텍스트가 아니라 “운영 가능/불가”, “원격 제어 가능/불가” 같은 의미로 표현해야 함.

## 3-2. 이벤트(Event)

장비에서 특정 일이 발생했을 때 시스템에 알려야 한다.

예)

- 공정 시작/종료
    
- Lot start / Lot end
    
- Recipe 변경
    
- 장비 모드 변경 등
    

이벤트는 보통 “이벤트 자체”만 보내는 게 아니라,  
**이벤트가 발생했을 때 어떤 데이터를 같이 보낼지(Report)** 와 연결된다.

## 3-3. 알람(Alarm)

장비에서 문제가 생기면 시스템이 즉시 알아야 한다.

- 알람 발생(Set)
    
- 알람 해제(Clear)
    
- 알람 코드/메시지/심각도
    

> UI에서 가장 중요한 화면 중 하나가 알람 리스트/히스토리다.

## 3-4. Report (이벤트 발생 시 묶어서 보내는 데이터)

이벤트가 발생하면 “그 이벤트와 함께 어떤 데이터들을 같이 보낼지”를 정의한다.

예)

- 이벤트: Lot Start
    
- Report: Lot ID, Recipe ID, Operator ID, 장비 상태 값 등
    

> GEM은 결국 “이벤트 + 리포트로 데이터 수집을 표준화”하는 게 핵심이다.

## 3-5. Remote Command (원격 명령)

시스템이 장비에 “원격으로 명령”을 내릴 수 있는 모델이다.

예)

- Start / Stop
    
- Recipe Select
    
- Pause / Resume
    

> 실무 포인트: 원격 명령은 안전 이슈가 많아서 장비가 Remote/Local 상태에 따라 허용/거부 로직이 들어가는 경우가 많다.
